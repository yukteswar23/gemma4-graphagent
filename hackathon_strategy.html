Core Thesis: The gap between cloud coding agents and local ones is not solely a weights problem — it is a structured state management problem. By grounding Gemma 4's reasoning in a persistent, AST-derived code graph and training it to use graph-navigation tools efficiently, we close the gap without requiring internet or datacenter hardware.
01 — The Problem

Why Coding Agents Fail Offline

Today's best coding agents — Devin, SWE-agent, Claude Code, Copilot Workspace — all share a critical dependency: cloud-hosted frontier models with hundreds of billions of parameters. This architectural choice is expensive, requires constant internet connectivity, exposes proprietary code to third-party servers, and is simply inaccessible to hundreds of millions of developers in cost-sensitive or air-gapped environments.

🌐
Cloud Only

GPT-4o / Claude 3.5 / Gemini Ultra

Require API calls to cloud. Code leaves your machine. Latency is unpredictable. Cost per complex fix: $1–50. Not accessible offline.

💻
Target: Local

Gemma 4 31B QAT (W4A16)

~17 GB VRAM. Runs on RTX 4090, Mac Studio M3, or Radeon RX 7900. No internet. Code stays local. Zero recurring cost.

Small local models have improved rapidly, yet they still fail on multi-turn, complex software engineering. The failures are not random — they cluster around three root causes:

🗺️
Failure Mode 1

Codebase Blindness

Without a structural index, the agent must spend precious context tokens on file reads and grep calls just to understand where the bug might live.

🔁
Failure Mode 2

State Amnesia

Each tool call returns partial info. Without a persistent evidence store, the agent re-discovers facts, loops, and eventually exhausts its tool budget.

🎯
Failure Mode 3

Patch Drift

Without knowing which symbols are interconnected via calls/imports, a patch fixes one site but silently breaks three dependents downstream.

The core problem is not model intelligence — it is structured context management. A 31B local model can reason perfectly well about a 50-line function. The challenge is helping it find the right 50 lines across a 500,000-line codebase using only 100 tool calls and a finite context window.

Industry Stakes

This problem is not academic. 76% of professional developers report using or planning to use AI coding tools in 2026, yet fewer than 20% can afford or are permitted to use cloud APIs for production codebases. Air-gapped environments (finance, defense, healthcare, embedded systems) represent enormous demand for local-capable autonomous agents. A solution that works offline on consumer hardware is worth billions.

03 — Our Approach

GraphAgent: Four Interlocking Innovations

We propose GraphAgent, a system that combines a persistent code-graph index with a graph-aware post-training recipe. The approach is grounded in a fundamental observation: the competition's evaluation harness already exposes code-graph tools (get_code_neighbors, search_similar_code, get_code_subgraph) — but no public model has been explicitly trained to use them efficiently.

Current State of Art
  • Uses grep + read_file blindly
  • Re-reads same files repeatedly
  • No dependency awareness in patches
  • Treats tools as interchangeable
  • Loses track of evidence across turns
  • No tool-call budget awareness
  • Generic training — not tool-specific
GraphAgent
  • Builds graph index first, then targets
  • Persistent evidence store prevents re-reads
  • Propagates fix across call-graph neighbors
  • Trained on tool-role-specific trajectories
  • Maintains hypothesis tree across turns
  • Explicit budget-aware tool selection policy
  • DR-LoRA fine-tuned on graph-nav trajectories
Innovation 1

Code Graph Constructor (CGC)

Tree-sitter + call-graph analysis produces a hierarchical AST-derived graph stored in-memory. Nodes are functions/classes/modules; edges are calls, imports, and inheritance. The CGC runs once at the start of each task episode and is reused across all tool calls. Reduces cold-start cost from ~20 tool calls to ~3.

Innovation 2

Dynamic-Rank LoRA (DR-LoRA)

Standard LoRA applies uniform ranks across layers. DR-LoRA assigns higher rank to attention layers involved in tool-call formatting (where precision matters most) and lower rank to FFN layers (where the coding knowledge already lives). Only ~2% of parameters are tunable — fits alongside the QAT base on a single GPU.

Innovation 3

Graph-RLVR Training

Reinforcement Learning with Verifiable Rewards: the reward signal comes from (a) patch execution success, (b) test suite pass rate, and (c) tool-call efficiency bonus (fewer calls to resolve = higher reward). No critic network needed — the environment itself provides dense feedback.

Innovation 4

Evidence Buffer (EB)

A lightweight key-value store that persists structured observations (file contents, symbol definitions, error messages, failed hypotheses) across turns. The model is trained to read and write to the EB rather than relying on context window recency. Prevents the "state amnesia" failure mode.

1

Issue Ingestion & Triage

Parse the bug report to extract: mentioned file paths, symbol names, error classes, stack trace frames, and reproduction steps. This structured triage forms the initial seed for the fault localization phase and prevents the model from making uninformed "random walk" tool calls.

2

Code Graph Construction (3 tool calls)

Call get_code_subgraph on seed symbols → build a local neighborhood graph. Call search_similar_code with issue keywords → surface semantically relevant functions. Call get_code_neighbors on top candidates → identify all callers/callees. After 3 calls, we have a targeted subgraph of ~20–50 relevant nodes — drastically smaller than the full repo.

3

Fault Localization via Structural Hypothesis

Using the code subgraph plus issue triage, generate a ranked hypothesis list: "Bug is most likely in module.ClassA.method_x (confidence 87%) because it is called from the stack trace entry point and its dependency on utils.parser matches the error class." Read only the top-ranked candidates.

4

Targeted File Read & Evidence Accumulation

Read only the files implicated by the top hypothesis. Write key facts (function signatures, variable names, error conditions) into the Evidence Buffer. The EB is a structured JSON store that persists across turns and replaces the need to re-read the same file multiple times — a major source of tool call waste.

5

Patch Synthesis with Dependency Awareness

Generate the fix for the primary location. Then, consult get_code_neighbors to check whether any callers depend on the changed signature/contract. If yes, propagate matching changes to dependents. This prevents the common failure mode where a correct local fix breaks downstream callers.

6

Verification Loop (run_command → submit_patch)

Run the test suite. If tests fail: read error output, update evidence buffer, revise the hypothesis, attempt fix at next-ranked candidate location. Only call submit_patch after tests pass or budget reaches ~85 calls. This prevents premature submission of broken patches.

05 — Training Strategy

Post-Training Recipe: SFT → RLVR

The post-training is a two-phase process. Phase 1 (SFT) instills the graph-navigation behavior patterns via supervised fine-tuning on curated trajectories. Phase 2 (RLVR) refines efficiency and correctness via reinforcement learning from execution feedback.

Phase 1: Graph-Aware Supervised Fine-Tuning

Dataset Construction: We synthesize 50,000 (issue, solution_trajectory) pairs from SWE-Gym and SWE-bench-verified. Each trajectory is post-processed to insert graph-navigation tool calls at optimal decision points. Trajectories with >80 tool calls are pruned. Trajectories where a graph call precedes the correct file read are up-weighted ×3.
Step-Level Masking

Train on Successes Only

For each trajectory, mask loss on steps that led to dead ends. Only compute loss on steps that contributed to the final successful patch. This prevents the model from learning failed navigation patterns.

DR-LoRA Config

Adaptive Rank Assignment

Attention (Q,K,V,O) layers: rank=64 (tool-call formatting, precision matters). FFN (gate, up, down): rank=16 (coding knowledge already strong). LoRA alpha=32. Dropout=0.05. Only ~2% trainable parameters.

Phase 2: Graph-RLVR (Reinforcement Learning with Verifiable Rewards)

No critic network required. The environment provides three verifiable reward signals: (1) Binary patch reward: did the submitted patch pass all tests? (+1.0 / 0.0) (2) Efficiency bonus: reward = 1.0 + (100 - tool_calls_used) / 100 * 0.3 (3) Graph-usage bonus: +0.1 for each graph tool call that correctly narrowed search space (verified by counterfactual: would the agent have found the bug without it?)
Reward SignalWeightSourcePurpose
Test Suite Pass1.0run_command outputCorrectness — primary objective
Tool Efficiency0.3Harness tool counterPenalizes wasteful navigation
Graph Tool Bonus0.1 eachCounterfactual evalEncourages structural navigation
No-Submission Penalty−0.5Episode end stateDiscourages giving up
Broken Patch Penalty−0.3Test outputDiscourages premature submission

We use GRPO (Group Relative Policy Optimization) as the RL algorithm — it is reference-model free, does not require a separate critic network, and has shown strong results on coding tasks in the SoRFT and RLEF papers. 8 parallel rollouts per update step. Learning rate 5e-6, KL penalty coefficient 0.1.

06 — Tool Strategy

Mastering the Harness Tools

The competition harness provides 9 tools. Most entries use them opportunistically. GraphAgent is explicitly trained to use each tool in a defined role, with a learned policy for when to call which tool based on the current state of the evidence buffer.

Tool Role in GraphAgent Typical Call Budget Stage
get_code_subgraph Initial structural map of seed symbols from issue 1–3 Triage
search_similar_code Semantic search to surface related functions 2–5 Localization
get_code_neighbors Callers/callees check before patching 2–4 Pre-patch + Post-patch
read_file Only after graph localization — read targeted files 3–8 Analysis
edit_file Apply patch with full context 1–5 Synthesis
write_file New files (tests, configs) if needed 0–2 Synthesis
run_command Test suite, linting, type check 3–10 Verification
submit_patch Only when tests pass or budget >85 calls 1 Submission
get_status Verify harness state after operations 1–3 Any
Budget Management Policy: The agent is trained to maintain a mental model of remaining tool calls. At >75 calls used: switch to "exploit" mode — stop exploring, commit to best hypothesis. At >90 calls: generate best-effort patch even if not fully verified. At exactly 99: submit whatever the current edit_file state is. This policy prevents the common failure of running out of budget with no submission.

GraphNav-Bench: Our New Resource (Paper Track)

We propose contributing GraphNav-Bench — a curated dataset of 500 SWE-bench-style issues explicitly labeled with the minimum set of graph tool calls needed to localize the bug. Each entry includes:

Dataset Field

Gold Navigation Path

The optimal sequence of get_code_subgraph / search_similar_code calls that reaches the bug in ≤5 calls.

Dataset Field

Minimum Tool Budget

Ground-truth minimum number of tool calls a perfect agent needs. Enables efficiency measurement beyond pass/fail.

Dataset Field

Difficulty Taxonomy

Each issue tagged by: localization difficulty (1–5), patch complexity (1–5), dependency blast radius (1–5).
